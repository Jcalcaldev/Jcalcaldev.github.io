A data layer that grew with the game One read model over database and blockchain data, rebuilt twice as we grew. 90% fasterread times

I built the read model that combines our database with on-chain ownership data, then rebuilt it twice: first as a PostgreSQL incrementally maintained materialized view, then as a projection kept up to date by triggers.

Read times dropped by about 90%. The trigger-based version also cut occasional slow updates on a 7.4M-row table from about 90 seconds to 100 ms.

PostgreSQL, PL/pgSQL, Graph Node subgraphs

Moving the data layer to Hasura Business rules moved into PostgreSQL, while features kept shipping. Every clientbound by the same rules in Postgres

I led an incremental migration from our original custom GraphQL service to Hasura, while features kept shipping.

Validation and business rules now live in PostgreSQL functions and triggers, so they hold no matter which client writes the data.

Hasura, PostgreSQL
